# 架构决策记录（ADR）

> 记录"为什么这么定"。冻结后变更先进 `change-log.md`，再改文档与代码。

## ADR-001：RAG 而非微调
- **决策**：采用检索增强生成（RAG），不做模型微调。
- **理由**：知识更新成本低（增删文档即可）、答案可追溯（带引用）、无需训练资源。
- **影响**：效果强依赖检索质量，必须配套评测体系（见 ADR-006）。

## ADR-002：向量库选 Chroma + 接口抽象
- **决策**：默认 Chroma，抽象 `VectorStore` 接口，提供 InMemory 回退。
- **理由**：Chroma 轻量、纯 Python、可持久化；抽象后便于迁移 Qdrant/Milvus。

## ADR-003：Embedding 用本地 sentence-transformers
- **决策**：默认本地 `BAAI/bge-small-zh-v1.5`，抽象 `EmbeddingProvider`，另支持 OpenAI 与 Hash。
- **理由**：本地免费、数据不外传、中文效果好；Hash 回退保证离线可测。

## ADR-004：LLM 用 OpenAI 兼容接口
- **决策**：`LLMClient` 面向 OpenAI 兼容 `/chat/completions`，默认 DeepSeek。
- **理由**：一套代码覆盖 OpenAI / DeepSeek / 智谱，降低切换成本。

## ADR-005：关系库选 MySQL（而非 SQLite）
- **决策**：V1 使用 MySQL 8 持久化元数据与会话。
- **理由**：用户目标是 Python 后端求职，MySQL 是主流数据库；SQLite 并发写受限。
- **权衡**：引入外部依赖（需装 MySQL），测试需连接真实库。

## ADR-006：必须做评测
- **决策**：提供测试集 + 关键词命中率 / 来源准确率 / 拒答正确率 / 综合准确率。
- **理由**：RAG 效果依赖 chunk / top_k / rerank 等参数，无评测无法证明"系统是好的"。
- **约束**：所有指标必须来自真实评测，不预设目标值。

## ADR-007：Router = 规则优先 + LLM 分类 + RAG 兜底
- **决策**：规则能判就不调 LLM；判不出才可选 LLM 分类；最终兜底 RAG。
- **理由**：减少 LLM 调用次数，更稳定、更省钱；RAG 是最稳且可追溯的默认路径。

## ADR-008：Agent 引用硬约束
- **决策**：Agent 涉及知识库事实时必须经 `knowledge_search` 取得依据；无依据不得编造引用，应拒答。
- **理由**：保护"可追溯 + 不知道就拒答"这一核心卖点，防止 Agent 编造来源。

## ADR-009：JWT + PBKDF2，单租户基础认证
- **决策**：JWT（PyJWT）+ PBKDF2 密码哈希；仅登录/注册/基础鉴权。
- **不做**：RBAC、组织架构、多租户、部门、ACL。
- **理由**：V1 单租户定位，避免权限系统导致范围膨胀。

## ADR-010：自研 ReAct 循环（理解原理，不排斥框架）
- **决策**：自己实现 ReAct 循环，以理解 Agent 内部机制；同时了解 LangChain / Dify 的设计与用法。
- **理由**：自研能讲清原理，框架提升效率，二者不冲突。

## ADR-011：Rerank 用 A/B 数据驱动
- **决策**：不预设必须用某模型；流程为"无 Rerank → 评测 → 加 Rerank → 评测 → 按数据决定"。
- **实测结论（2026-09 初版）**：5 题小数据集上 Noop 与 bge-reranker-base 持平（均 100%），原因是单文档单 chunk、重排无发挥空间 → **V1 保持不启用**，留待更大语料重测。
- **复测结论（2026-09-14，语料已扩充，推翻旧的"没发挥空间"理由）**：
  语料 2 → **6 文档 / 13 chunk**（含 2 个近邻干扰），测试集 5 → **47 题**。
  此时评测指标已**饱和**（两组都 100%），因此改用有区分度的**排序质量 + 延迟成本**做 A/B
  （脚本 `scripts/rerank_ab.py`，原始数据 `data/rerank_ab_prod.json`，生产配置：候选 5 → 最终 3）：

  | 指标 | A 组 Noop（现状） | B 组 bge-reranker-base | 变化 |
  | --- | --- | --- | --- |
  | Recall@1 | 92.3% | 94.9% | +2.6pp |
  | Recall@3（最终集合） | **100%** | **100%** | 0 |
  | MRR | 0.9573 | 0.9744 | +0.0171 |
  | 检索延迟（均值） | **9.3 ms** | **1236 ms** | **132.9×** |
  | 未命中 | 0 | 0 | 0 |

- **决策（维持不启用）**：重排只把正确答案从第 2 名提到第 1 名，**不改变可达性**
  （最终集合召回两组都是 100%），而代价是每次检索从 9ms 涨到 **1.2 秒（133 倍）** ——
  对交互式问答不可接受，对答案正确率也没有可测收益。
  → **V1 保持 `ENABLE_RERANK=false`**。
- **复测结论（2026-09-14，大语料：把干扰扩到 20 倍，结论比 13 chunk 时更强）**：
  用 `scripts/gen_corpus.py --include-base` 造合并语料 **`data/kb_large`**
  （原始 6 篇 + 60 篇同话题干扰，共 66 篇 / **190 chunk**，固定种子 20260101 可逐字节复现），
  跑同一 A/B（`scripts/rerank_ab.py`，原始数据 `data/rerank_ab_large.json`，
  候选数扫描 `data/rerank_ab_large_sweep.json`；真实 bge-small-zh + 真实 bge-reranker-base + 真实 Chroma）：

  | 指标（候选 5） | A 组 Noop | B 组 bge-reranker-base | 变化 |
  | --- | --- | --- | --- |
  | Recall@1 | 79.5% | 79.5% | **+0.0pp** |
  | Recall@5 | 92.3% | 92.3% | 0 |
  | MRR | 0.8470 | 0.8526 | +0.0056 |
  | 检索延迟 p50 | **16.7 ms** | **1420.9 ms** | **85×** |

  **候选集召回上限**（正确文档是否还在候选里 —— 这是重排的天花板）：
  候选 5 → 92.3%、10 → 97.4%、**20 → 100%**、40 → 100%。
  重排延迟随候选数**线性增长，约 280~300 ms / 候选**（5→1.46 s、10→2.84 s、20→6.17 s）。

- **决策（维持不启用，理由更强了）**：噪声语料下，候选 5 时已有 **3/39 题的正确文档根本不在候选集内**，
  重排无从发挥 → R@1 零增益；把候选抬到 20 才把天花板拉回 100%，此时 R@1 才 +2.6pp / MRR +0.044，
  但单次检索要 **6.2 秒**。即：**重排的收益窗口 = "候选集仍含正确文档、但被噪声挤到第 2 名之后"**，
  而这个窗口的代价是 85~133× 延迟，交互式问答不可接受 → **保持 `ENABLE_RERANK=false`**。
  将来若要做，正确形态是"更小的 reranker + 更小候选集 + 异步"，而不是把 base 模型塞进同步检索路径。

- **语料目录说明（避免重复踩坑）**：
  `data/kb`（6 篇 / 13 chunk）是**唯一参与日常评测与默认索引**的目录；
  `data/kb_ext`（60 篇 / 177 chunk）是**纯干扰**语料；
  `data/kb_large`（66 篇 / 190 chunk）是二者合并，仅用于上面的重排 A/B 与压测。
  ⚠️ 用 `rebuild_kb.py --kb-dir data/kb_ext` **整体替换**索引会让金标准文档全部不在库里，
  评测必然全 0（这个坑真实踩过一次）；混合口径实验必须用 `kb_large` 这类**包含金标准**的目录。

- **口径声明**：39 道可答题**没有 chunk 级相关性标注**，所以 MRR 只反映"标准出处文档的名次"，
  不等于"语义效果变好"；这也是为什么 `presence`（候选集是否命中）必须与 R@1/MRR 一起报。

## ADR-013：检索相似度阈值（MIN_SCORE）默认关闭 —— 实测本语料下无区分度

- **背景**：V2 引入 `MIN_SCORE`，期望"低分片段直接过滤掉，把拒答从模型侧提前到检索侧"。
  但阈值定多少不能拍脑袋，于是先用真实 bge + 真实索引做了分数分布校准。

- **实测（2026-09-14，6 文档 / 13 chunk，39 道可答题，`top_k=5`）**：

  | 对象 | 分数区间 |
  | --- | --- |
  | **金标准片段** | min **0.4477** / p5 0.4925 / mean 0.6283 / max 0.7470 |
  | **干扰片段**（n=156） | mean **0.5285** / max 0.6976 |

  | 阈值 | 保留金标准 | 过滤干扰 | 判定 |
  | --- | --- | --- | --- |
  | 0.0 ~ 0.3 | 39/39 | 0/156 | 完全不起作用 |
  | **0.4** | 39/39 | 4/156（2.6%） | 安全但几乎无效 |
  | 0.5 | **37/39**（误杀 2） | 61/156 | 开始有害 |
  | 0.6 | **27/39**（误杀 12） | 126/156 | 明显有害 |

- **结论**：bge-small-zh 的余弦相似度被压缩在 0.45~0.75 区间，**相关与不相关高度重叠**，
  不存在能把两者分开的阈值 —— 最优安全上界 0.4477 只能过滤 2.6% 的噪声，收益可忽略；
  而一旦调到 0.5 就开始误杀正确答案。→ **默认保持 `MIN_SCORE=0.0`（关闭）**。

- **保留该项能力的理由**：换 embedding 模型（例如更大的 bge-m3、或领域微调模型）后分数分布会变，
  届时用同一脚本重测即可启用；接口与配置都已就绪（`VectorStore.query(min_score=...)`）。

- **更可能的正确方向（登记待验证）**：与其用绝对阈值，不如用**相对判据**
  （例如"top1 与 top2 的分数差"或"rerank 后的 cross-encoder 分数"）。
  但 cross-encoder 在 20 候选下实测单次检索 **5.5 秒**，代价过高（见 ADR-011 复测），
  短期内仍以 **Prompt 硬约束 + 拒答评测** 作为拒答主力。
