# 架构决策记录（ADR）

> 记录"为什么这么定"。冻结后变更先进 `change-log.md`，再改文档与代码。

## ADR-001：RAG 而非微调
- **决策**：采用检索增强生成（RAG），不做模型微调。
- **理由**：知识更新成本低（增删文档即可）、答案可追溯（带引用）、无需训练资源。
- **影响**：效果强依赖检索质量，必须配套评测体系（见 ADR-006）。

## ADR-002：向量库选 Chroma + 接口抽象
- **决策**：默认 Chroma，抽象 `VectorStore` 接口，提供 InMemory 回退。
- **理由**：Chroma 轻量、纯 Python、可持久化；抽象后便于迁移 Qdrant/Milvus。

## ADR-003：Embedding 用本地 sentence-transformers
- **决策**：默认本地 `BAAI/bge-small-zh-v1.5`，抽象 `EmbeddingProvider`，另支持 OpenAI 与 Hash。
- **理由**：本地免费、数据不外传、中文效果好；Hash 回退保证离线可测。

## ADR-004：LLM 用 OpenAI 兼容接口
- **决策**：`LLMClient` 面向 OpenAI 兼容 `/chat/completions`，默认 DeepSeek。
- **理由**：一套代码覆盖 OpenAI / DeepSeek / 智谱，降低切换成本。

## ADR-005：关系库选 MySQL（而非 SQLite）
- **决策**：V1 使用 MySQL 8 持久化元数据与会话。
- **理由**：用户目标是 Python 后端求职，MySQL 是主流数据库；SQLite 并发写受限。
- **权衡**：引入外部依赖（需装 MySQL），测试需连接真实库。

## ADR-006：必须做评测
- **决策**：提供测试集 + 关键词命中率 / 来源准确率 / 拒答正确率 / 综合准确率。
- **理由**：RAG 效果依赖 chunk / top_k / rerank 等参数，无评测无法证明"系统是好的"。
- **约束**：所有指标必须来自真实评测，不预设目标值。

## ADR-007：Router = 规则优先 + LLM 分类 + RAG 兜底
- **决策**：规则能判就不调 LLM；判不出才可选 LLM 分类；最终兜底 RAG。
- **理由**：减少 LLM 调用次数，更稳定、更省钱；RAG 是最稳且可追溯的默认路径。

## ADR-008：Agent 引用硬约束
- **决策**：Agent 涉及知识库事实时必须经 `knowledge_search` 取得依据；无依据不得编造引用，应拒答。
- **理由**：保护"可追溯 + 不知道就拒答"这一核心卖点，防止 Agent 编造来源。

## ADR-009：JWT + PBKDF2，单租户基础认证
- **决策**：JWT（PyJWT）+ PBKDF2 密码哈希；仅登录/注册/基础鉴权。
- **不做**：RBAC、组织架构、多租户、部门、ACL。
- **理由**：V1 单租户定位，避免权限系统导致范围膨胀。

## ADR-010：自研 ReAct 循环（理解原理，不排斥框架）
- **决策**：自己实现 ReAct 循环，以理解 Agent 内部机制；同时了解 LangChain / Dify 的设计与用法。
- **理由**：自研能讲清原理，框架提升效率，二者不冲突。

## ADR-011：Rerank 用 A/B 数据驱动
- **决策**：不预设必须用某模型；流程为"无 Rerank → 评测 → 加 Rerank → 评测 → 按数据决定"。
- **实测结论（2026-09 初版）**：5 题小数据集上 Noop 与 bge-reranker-base 持平（均 100%），原因是单文档单 chunk、重排无发挥空间 → **V1 保持不启用**，留待更大语料重测。
- **复测结论（2026-09-14，语料已扩充，推翻旧的"没发挥空间"理由）**：
  语料 2 → **6 文档 / 13 chunk**（含 2 个近邻干扰），测试集 5 → **47 题**。
  此时评测指标已**饱和**（两组都 100%），因此改用有区分度的**排序质量 + 延迟成本**做 A/B
  （脚本 `scripts/rerank_ab.py`，原始数据 `data/rerank_ab_prod.json`，生产配置：候选 5 → 最终 3）：

  | 指标 | A 组 Noop（现状） | B 组 bge-reranker-base | 变化 |
  | --- | --- | --- | --- |
  | Recall@1 | 92.3% | 94.9% | +2.6pp |
  | Recall@3（最终集合） | **100%** | **100%** | 0 |
  | MRR | 0.9573 | 0.9744 | +0.0171 |
  | 检索延迟（均值） | **9.3 ms** | **1236 ms** | **132.9×** |
  | 未命中 | 0 | 0 | 0 |

- **决策（维持不启用）**：重排只把正确答案从第 2 名提到第 1 名，**不改变可达性**
  （最终集合召回两组都是 100%），而代价是每次检索从 9ms 涨到 **1.2 秒（133 倍）** ——
  对交互式问答不可接受，对答案正确率也没有可测收益。
  → **V1 保持 `ENABLE_RERANK=false`**。
- **适用边界（诚实声明）**：本结论基于 6 文档 / 13 chunk 的语料。若语料继续扩容到数百 chunk，
  "候选集里是否还包含正确文档"会重新变成瓶颈，届时需按同一脚本复测；
  重排的价值通常在**候选多、噪声大**时体现，而不是在当前这个规模。

## ADR-012：新项目独立开发，旧项目作参考
- **决策**：`smart-kb-agent` 独立开发，`kb-ai-agent` 作为复用参考与回滚版本。
- **理由**：旧项目是技术 demo，新项目是产品化；保留演进叙事，也便于回滚。
